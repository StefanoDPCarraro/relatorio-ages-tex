\subsection{Repositório do Código Fonte do Projeto}
  Os repositórios foram divididos entre \textit{front-end} e \textit{back-end}. Em ambos, foi
determinado um padrão de \textit{commit} estruturado da seguinte maneira: tipo(id \textit{user story}): descrição, sendo que a mensagem pode conter no máximo 75 caracteres
para incentivar resumos. O padrão adotado segue o do Conventional Commits que
busca padronizar e manter relevantes, como histórico, os \textit{commits} de um repositório
\cite{conventionalcommits}.
Já as \textit{branches} seguem um padrão inspirado no GitFlow, aprendido na aula
de Gerenciamento e Configuração de Software, estruturado ao redor das \textit{branches}
\textit{main} e \textit{develop}, com cada \textit{branch} nova seguindo a estrutura tipo/id-\textit{task}/nome,
garantindo melhor organização na parte do versionamento \cite{atlassian-gitflow}.
Além disso, é notório o uso de \textit{linters} para forçar que a equipe siga esses
padrões, tanto na parte das \textit{branches} quanto dos \textit{commits}.

\subsection{Banco de Dados Utilizado}
  Por uma soma de fatores, como indicação dos \textit{stakeholders} e
convencionalidade de iniciar o projeto a partir de um banco de dados relacional já
existente da Receita, o time optou, de primeira mão, por continuar no caminho dos
bancos de dados relacionais.

Dentre eles, o PostgreSQL foi a nossa escolha \cite{postgresql-docs}, sendo influenciado por fatores
como domínio do mercado, facilidade de escrita e similaridade com as sintaxes
aprendidas nas matérias de Banco de Dados. Além disso, a robustez e capacidade
de lidar com volumes imensos de dados são características essenciais para nosso
projeto, disponibilizadas pelo PostgreSQL.

  \begin{figure}[H]
    \centering
    \small
    \caption{Modelagem do Banco de Dados - Indústria Digital}
    \includegraphics[width=1\linewidth]{conteudo//3 - ages II//conteudo//figures/industria-digital-database.png}
    Fonte: Wiki do Projeto
    \label{fig:database-industria-digital}
\end{figure}

  Como o trabalho tinha o intuito de ser uma prova de conceito, fizemos grande
parte com apenas uma parcela do banco de dados da Receita. Portanto, foi fundamental
que a equipe deixasse salvo todo \textit{script} rodado que modificava o banco de dados, já
que eles precisavam ser rodados novamente a cada troca de banco. Exemplos de
modificações que viraram \textit{scripts} são conversões de tipo, como \ac{cnpj} e id, que foram
passados de número para \textit{string}; criação de campos novos, como uma chave
primária estabelecimento\_id, para substituir a chave composta que antes era
utilizada; e remoção de campos irrelevantes para o projeto, como fax e ente
federativo responsável, para deixar o banco mais leve. Além disso, colocamos uf
como um atributo da tabela de municípios para facilitar a busca.

Além disso, para a conversa do \textit{back-end} com o banco de dados, estamos
utilizando o \ac{orm} SQLAlchemy \cite{sqlalchemy-docs}, responsável por facilitar a comunicação entre os
dois.

\subsection{Arquitetura Utilizada}
  Como mostrado na imagem abaixo, o fluxo de informações no aplicativo
começa pela parte do usuário, que interage com o \textit{front-end}; ele, por sua vez,
transforma essa interação em uma requisição \ac{http} que é enviada para o \textit{back-end},
responsável por tratar o \textit{request} e transformá-lo em uma \textit{query} de SQL com a ajuda do
SQLAlchemy, chegando, portanto, no banco de dados. A partir disso é percorrido o
caminho reverso, com o banco retornando o resultado de uma \textit{query} ao \textit{back-end},
que transforma essa \textit{query} em um \textit{payload} \ac{json}, recebido pelo \textit{front-end} e
finalmente atualizando a interface do usuário.

  A ideia da implementação de tal arquitetura tem como intuito uma separação
nítida das responsabilidades que cada parte do sistema desempenhará, deixando ao
Angular \cite{angular-docs}, no \textit{front-end}, a responsabilidade visual; ao FastAPI
\cite{fastapi-docs}, no \textit{back-end}, as restrições de
negócios e processamento de dados e finalmente ao PostgreSQL no banco de
dados, a persistência deles.

\subsection{Protótipos das Telas Desenvolvidas}
  Foi feito um protótipo no Figma \cite{figma-help} para definir o \textit{design} das telas a serem
desenvolvidas. Nele, houve 3 versões diferentes, apresentadas ao cliente e, por fim,
atualizadas conforme o \textit{feedback}.

  O desenvolvimento dos protótipos começou pela definição de uma identidade
visual para o projeto. Devido à existência de uma identidade visual no \textit{logo} de
nossos \textit{stakeholders}, decidimos manter as cores lá presentes, complementando com
uma variação mais leve de azul.

  Quanto às telas, foram criadas uma \textit{landing page}, três telas de dados e dois
modais para filtros. A ideia do fluxo é que, ao chegar, o usuário caia na \textit{landing page},
onde é obrigado a escolher filtros para iniciar a pesquisa. Ao selecionar os filtros
desejados, o usuário pode prosseguir para a pesquisa.

\subsection{Tecnologias Utilizadas}

  Era especificação do termo de abertura de projeto que o cliente gostaria que
fosse usada a linguagem Python \cite{python-docs} para o desenvolvimento do \textit{back-end} do projeto,
mais especificamente Django \cite{django-docs}. Ainda assim, após votação e pesquisa feitas em sala
de aula, decidimos que gostaríamos de usar Python, no entanto com o uso da
FastAPI, considerando aspectos como simplicidade, modernidade e principalmente
\textit{performance} disponibilizados pelo \textit{framework}. Sendo assim, conversamos com o
cliente e ele permitiu o uso da tecnologia, principalmente devido ao consenso e à
convicção que o time tinha quanto à importância do FastAPI.

Além disso, para realizar \textit{queries}, adicionamos o \ac{orm} SQLAlchemy,
responsável por facilitar o processo de comunicação entre banco e \textit{back-end}, devido à
compatibilidade que ele tem com PostgreSQL e Python.

Já o \textit{front-end} não era algo de total interesse do cliente, portanto, ele permitiu
que ficasse a nosso cargo a escolha. Em uma votação acirrada entre Next e
Angular, decidimos pelo segundo, visto a disparidade de conhecimento em Angular
por parte dos membros do time, já que muitos não sabiam, mas os poucos que
sabiam dominavam a linguagem, permitindo uma troca de informações resultante
em um aprendizado gigantesco por parte dos que não sabiam, combinado com um
conforto em saber que, em momentos de pânico, temos desenvolvedores com
conhecimento suficiente para resolver.

Por fim, junto com o Angular, utilizamos TypeScript \cite{typescript-docs} para lógica, \ac{html} puro
para linguagem de marcação e \ac{css} puro para a estilização da página.
